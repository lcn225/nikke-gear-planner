## R1 — 历史记录模式下的角色培养榜

### R1a 缺陷：加载历史后状态错配（**已于 2026-09-29 修复**）

> **已修**。修法与下述期望行为一致，并额外消除了一个副作用 —— 见本节末「实施记录」。
> 现象 / 根因留档，供回顾。

**现象**：先「运行计算」、再从侧边栏加载一份旧历史，角色培养榜会照常渲染
（不空、不报错），但内容是错的。

**根因**：`app.py` 的 `history_loaded` 分支（修复前在 409-442 行，
修复后是 419-465 行）覆盖了
`bids / stats / stones / credits`，但**没有清掉 `characters` 与 `unmet_primary`**。
于是角色榜拿着「新名册 × 旧竞价」渲染：

- 「毕业进度」列来自新名册的 `Character` 快照（新）
- 「下一步 / 成本(石) / ROI」列来自旧 `bids`（旧）
- ⏸ 门禁标记来自旧 `unmet_primary`（旧）

看上去一切正常，实际是错配。属于「把不知道伪装成知道」，与项目铁律冲突。

**期望行为**：加载历史时必须同时把 `characters`、`unmet_primary` 置空
（或显式保留并在界面上标注来源），不允许两者跨越来源混用。

**涉及模块**：`app.py`（history_loaded 分支、角色榜渲染前的 `saved_characters` 取值）

#### 实施记录（2026-09-29）

按期望行为把 `characters` / `unmet_primary` 纳入历史加载分支的统一处置，**但不是无条件置空**。

**为什么要分层**：无条件置空会带来一个明显副作用 ——
「运行计算 → 点侧边栏刚自动保存的那条历史 → 角色榜消失」，
而这条路径恰恰是最常用的，且此时名册与竞价其实是**同一次计算**的产物，
置空是「把知道伪装成不知道」，与铁律同样冲突。

**判据（可证明的同源，不是猜）**：`app.py` 运行计算成功后把
`save_history` 返回的路径记进 `session_state.last_run_history_path`，
连同名册与门禁结果的快照 `last_run_characters` / `last_run_unmet_primary`；
侧边栏加载时记下被点的 `history_path`。加载分支比对两者：

- **路径相同** → 这份历史就是上一轮自己存出去的 → 借用快照，角色榜照常显示
- **路径不同**（含冷启动、无路径可比）→ 一律置空，回落到「无法重建」说明文字

路径先清空、保存成功后才写入，因此**保存失败时不会留下上一轮的路径**被误判成同源。
判定同时要求 `history_path` 非空，避免「两个 None 相等」这种退化命中。

**附带确认**：`BidEntry` 共 14 个字段，`save_history` 全部落盘，
所以同源借用的快照与历史重建出的 `bids` 是逐字段一致的（round-trip 无损）。

**验证**：`py_compile` 通过；判定逻辑另行走了一遍 6 场景真值表
（同源/异源/冷启动/保存失败/无路径可比/来回切换）全部符合预期。
⚠️ WSL 侧无 streamlit，**渲染层未实测**，GUI 行为仍需在 Windows 侧确认。
⚠️ 那次真值表跑的是**复刻的判定逻辑**，不是 `app.py` 本身。
（2026-09-29 晚：这段判定已移入 `history_manager.resolve_replay`，
真值表改成测真函数，见 R1b 的实施记录。）

### R1b 历史记录不含名册，无法重建角色榜（**已于 2026-09-29 修复**）

**现象**：冷启动直接加载历史，角色榜位置显示一段说明文字，只有明细竞价天梯。

**根因（当时是刻意设计，非 bug）**：`history_manager.save_history` 只存
`bids`，不存 `Character` 名册快照。而角色榜是 `f(名册, 竞价, unmet_primary)`
三输入的函数，缺名册重建不出来。空名册会被判成「所有角色已毕业」，
所以加了门禁宁可显示说明文字。

**期望行为（定稿）**：历史记录**自包含** —— 存下一次计算的全部输入，
冷启动加载旧历史能重建出与当时一模一样的角色榜。

**涉及模块**：`history_manager.py`、`models/targets.py`、`app.py`

#### 实施记录（2026-09-29）

**存什么**。一条记录 = 一次计算的可回放快照，新增四个字段：

| 字段 | 内容 | 体积 |
|---|---|---|
| `mode` | 本跑用的养成目标模式（PVE/PVP） | 极小 |
| `roster` | 名册装备快照（`Character.to_dict()` × N） | ~96KB |
| `targets` | 该模式下这批角色的目标切片 | ~79KB |
| `unmet_primary` | 引擎的 primary 门禁结果 | ~1KB |

**为什么目标也要存**（而不是只存名册）。目标取自
`data/targets_parsed.json`（随仓库分发的快照）。只存名册、目标现取的话，
目标表一更新，重建出来的就是「旧名册 × 新目标」—— 混源换了个入口进来，
和 R1a 是同一个毛病。模式也一样：同一份名册在 PVE / PVP 下是两份完全不同的榜，
不存模式就无从知道该配哪份目标。

代价：每份 899KB → 约 1.07MB（+19%）。界面上本来就显示总体积与单份体积，
7 份约 7.5MB，可接受。

**存的是原始切片，不是解析结果**。`targets` 存的是
`targets_parsed.json` 的**原始条目**（只留 `tier`/`scores`/`modes[mode]`），
读回时走同一个 `_char_targets` —— 与当次跑计算是同一条解析路径。
存解析结果等于把解析逻辑抄一份进历史文件，两边一旦走偏，从文件本身看不出来。

**判定逻辑从 `app.py` 移出**。R1a 的同源借用判定原先内联在 `app.py` 的加载分支里，
WSL 侧 import 不了 streamlit，只能靠**复刻**逻辑做真值表。现在整段决策是
`history_manager.resolve_replay()`（纯函数，四种来源：自包含 / 记录损坏 /
旧记录同源借用 / 旧记录异源），真值表测的是**真函数**而不是复刻品。
渲染层只剩「把结果写进 session_state」和文案。

**顺带修掉一个假话**。`app.py` 的自动保存原先把整个 `save_history` 包进
`try/except`，except 里照样打印「💾 已自动保存历史记录」—— 保存失败也这么说。
那个 except 本意只是兜 `st.toast` 在 Streamlit <1.30 不可用。现已拆开：
保存失败 `st.warning` 报出来，toast 失败才降级为 success。
这条路径还决定了「加载历史时能不能借用名册」，静默失败会让人以为记录在。

**验证**：

- ✅ `py_compile` 通过；静态审计了 `app.py` 全部 16 个 session_state 业务键的读写点
- ✅ 新增 `test_history_snapshot_roundtrip`：跑引擎 → 存 → 读回 → **角色榜逐行全等**
  （PVE/PVP 各一遍）。同时钉住「旧格式记录读成 `None`」「缺目标切片要抛错」
  「拿错模式读切片要抛错」
  - 敏感性已验证：故意换成另一套目标重建，9 行里有 7 行的「毕业进度」会变
    —— 说明这条断言真的能拦住混源，不是恒真
- ✅ 新增 `test_history_replay_resolution`：7 场景真值表（自包含 / 损坏 / 同源借用 /
  异源 / 冷启动 / 保存失败 / 来回切换）
- ⚠️ **渲染层仍未实测**：WSL 侧无 streamlit，`app.py` 一行都跑不了。
  GUI 行为（侧边栏按钮文案、模式提示、错误提示的位置）仍需在 Windows 侧确认

复测建议：跑一次计算 → 关掉页面重开（模拟冷启动）→ 直接点最新那条历史，
角色榜应**照常显示**；再点一条 9/27 之前的旧记录，应显示「旧格式」说明文字。

## R2 — GUI 勾选「已完成」，免去重新 OCR 看反馈

**现象**：对照培养方案在游戏里实际操作后，想看到「这条做完了、下一条是什么」，
现在必须走 重新 OCR → 重新读 JSON → 重新计算 一整圈。

**期望行为**：在明细竞价天梯（以及角色榜）的每行加勾选。勾选语义就是
**「这条建议我已经做完了」**，然后用户自己去看下一条。

- **不重新计算**。天梯次序在算出那一刻已经定好，勾掉一行不改变其余行的相对顺序。
- 视觉上区分已完成行（划掉 / 变灰）。
- 角色榜联动：该角色推进到**下一条候选动作**。这不需要重算 ——
  `bids` 里本来就存了该角色的全部候选，`build_character_ladder` 只是取了
  `sort_score` 最高的那条，改取次高即可（查表，非重算）。
- 不做资源扣减、不做词条套用、不假设随机结果 —— 那些是「重新计算」路线才需要的，
  本需求明确不走那条路。

**涉及模块**：`app.py`（角色榜与明细天梯的渲染）、`ui_backend.py`
（可能需要一个「取该角色下一候选」的查询函数）

**备注（待定项）**：勾选状态存哪。
- 仅存 session：实现最简，刷新/重开即失效
- 存 `data/progress.json` 并绑定到某次历史记录：跨会话保留
- 写回历史文件：不推荐，会让历史文件既不是纯结果回放、又要防重算覆盖

倾向第二个，但按最小实现可以先走 session，需要时再升级。

（2026-09-29：R1b 已让历史记录自包含。「绑定某次历史」现在真能落地 ——
绑定一条历史就等于绑定它自带的名册、目标与门禁，勾选状态读回来时
能跟当时的角色榜对齐。之前绑过去也只能绑到一份没有名册的记录。）

#### 实施记录（2026-10-15）

**状态存哪：定的是「仅 session」那一档**，没有走 `data/progress.json`。
代价写在明面上：**刷新页面（F5）或关掉浏览器，勾选就没了**。
判定逻辑全部做成了纯函数（见下），将来要升级成「绑定某次历史记录」，
只需要把 `st.session_state.done_actions` 换成一层读写 `data/progress.json`
的存储，键用那份历史的文件路径 —— 界面与语义都不用动。

**「勾选状态属于哪一份结果」有明确边界**。换一份结果（**重新计算**或**加载另一条历史**）
即清空并换一个 `run_seq`，规则与 `history_mode` 那几个标注字段同一处置。
不清空的话，同一串键在 PVE / PVP 两份目标下指向的东西可能已经不一样了 ——
那就是 R1a 那类混源，只是换了个入口进来。所以：一个勾选清单只属于一份名册 + 一份竞价。

**「推进到下一条」没有新算法**。`build_character_ladder` 本来就取该角色
`sort_score` 最高的那条候选；把已勾的从喂进去的 `bids` 里滤掉，它自己就落到次高。
所以 `filter_done_bids` 只是「滤」，没有任何排序或重算逻辑。
明细天梯反过来拿**全量**——已勾的行留在原位（次序不变），只是标出来。

**动作身份**：键 = `角色 | 部位 | 操作 | 目标组合`（`BidEntry.action_key`）。
**不能拿 `action_detail` 当键** —— 升级类的详情里不含角色名
（`"消耗 20k 信用点强化手部基础攻击面板 (Lv0→Lv1)"`），两个角色同部位同等级会撞成同一个键。
实测：本仓 1502 条竞价里 `action_detail` 有 **7 组重复**，而本键 PVE/PVP 两跑都是 **0 组**
（1502 / 1507 条）。

**回写只动屏幕上出现的那几行**（`merge_done_flags`）。表格控件只能看到
top_n 与当前筛选之后的那一段，没显示的行不在回读结果里 ——
整集合覆盖式回写的话，用户切一下筛选条件就会把别的行的勾选抹掉。
控件 key 带上 `run_seq + top_n + 筛选签名`：行集一变就换控件，
免得编辑框按行号把勾选回填到另一批行上。

**候选被全部勾掉的角色**走既有的 `unavailable` 通路，显示「已全部勾选完成」。
不这么做的话它们会显示「已无待办动作」—— 那是假话，动作是用户自己勾掉的。

**一处刻意的偏差：没有「划掉 / 变灰」**。Pandas Styler 的样式在
`st.data_editor` 里**只对 disabled 列生效**，而且给编辑框套 Styler 会让控件**丢状态**
（streamlit#6898）。拿勾选框本身去换一个变灰效果不划算 —— 本机装不了 streamlit，
这条没法实测，所以选了低风险方案：已勾的行在「详情」单元格前面加显式标记
`✅ 已完成 · `，加上第一列的勾选框。真想要划线效果，得退回只读表格（那样就没有勾选框了）。

**未做（明确的，不是漏掉的）**：导出 CSV / 执行清单**不**按勾选过滤，导出契约不变；
展开详情里的候选表不加勾选框（勾选中枢是明细天梯 + 详情顶部的「✅ 做完了」按钮）；
勾选**不写回历史文件**（会破坏「历史 = 纯结果回放」的性质，本页开头已否决）。

## R3 — 魔方升级效果计算器

**登记于 2026-09-27。状态：需求已记下，细节待定。**
用户原话：「记录一个需求：魔方升级效果计算器」。**下次推进前先读「必须先定」那一节**，
它列出了现在缺什么 —— 缺的东西不补齐就不要动手实现。

### 现象 / 缘起

现有引擎只覆盖 **头 / 甲 / 手 / 脚 四槽过载装备**。魔方（Cube）是另一类装备，
它的加成会挤占**同一份属性预算**，但项目目前对它一无所知。

### 现有资料里魔方的全部证据（只有 1 行）

`data/targets.json:2388`（原始 wiki 快照，尚未清洗进 `targets_parsed.json`），
某角色的 PVP 面板指令：

> 18%以上蓄力速度达标，配合充能魔方，蓄速词条达到21%以上毕业。

- **入库文件 `git grep 魔方` 零命中**；全盘扫描（`command grep`）也只有上面这一条。
- 没有魔方种类列表、没有等级表、没有升级消耗、没有采集字段。

### 能从现有代码确定性推出的（已核对过代码，不是猜测）

1. **插点是现成的，不必新增乘区（前提见「必须先定」第 3 条）。**
   `engine/damage_model.py` 消费的是「词条名 → 百分比」的汇总
   （`攻击力增加`→atk、`蓄力速度增加`→cs_pct …），魔方加成汇进同一个汇总即可，
   五大乘区会自动处理稀释。
2. **蓄速这条咬合得最紧，且不只是「算个 delta」。**
   `compute_m_cs` 用的是 `min(cs_threshold, cs_ol)` —— 越过秒蓄线后，
   多余蓄速收益**恒等于 0**。所以充能魔方的真实价值是**重算词条预算**：
   魔方给 X%，装备就只需补 `21% − X%`。这正是上面那句话在说的事。

   ⚠️ 推论：魔方会**反向影响现有的目标达成判定**，而不仅是「多一类动作」。
   涉及 `models/targets.py` 的进度计算与 `engine/bidding_engine.py` 的 primary 门禁。
3. **数据归属明确**：魔方等级属于「账号现状」（每次玩都变），
   按项目的数据源分工应进 `input/`，**不是** `data/` 里的静态快照。

### 必须先定（下次推进的起点）

1. **「效果计算器」输出什么？** 三个层次差很多：
   单角色收益换算（面板 / 伤害 delta）、魔方之间的升级排序、并入全局竞价天梯。
   最后一档需要额外的 ΔC 与库存字段才能算 ROI。
2. **数据从哪来？** 等级表 + 每级效果 + 升级材料消耗，谁来提供。
   ⚠️ **ΔC 缺失则任何 ROI 都算不了**，只能退化成纯数值查询。
3. **魔方加成算哪一类？** 与过载词条**同源加算**，还是**独立乘区**。

### 1. 控制台编码降级（`4041033`）

中文 Windows 上 stdout 被**重定向或管道捕获**时编码是 GBK，`print("❌ …")` 抛
UnicodeEncodeError（真实控制台不受影响，Python 走 WriteConsoleW）。测试运行器的
失败报告里正有这么一句，于是「一条失败不终止整轮」这个立意被它自己打死了 ——
一条失败就整轮中止，后面没跑的测试**不留任何痕迹**。

新增 `console_io.py`：注册 codec 错误处理器，只在真的编不出来时降级成等义 ASCII
（`✅`→`[OK]`、`⚠`→`[WARN]`，装饰性 emoji → `[*]`）。UTF-8 环境（WSL、真实控制台）
下输出逐字节不变。顺带修了 `test_alias_coverage` 里 subprocess 父子两端编码口径
不一致的同源 bug（带 `PYTHONIOENCODING=utf-8` 跑必挂）。

## 讨论中已否决的方案（留档，避免重复提）

R2 最初考虑过「勾选 → 本地套用动作效果 → 重算 → 天梯实时刷新」。否决原因：

- 洗词条 / 洗数值的结果是游戏随机滚出来的，程序无法推导。
  自动假设结果（哪怕最好/最坏情况）等于编数据。
- 确定性操作（升级、开光）虽然可推导，但那只是把「重算」缩到一半，
  仍然要维护一套 apply 逻辑 —— 与「勾一下、看下一条」的实际使用方式不匹配。

结论：勾选就是打标记，不做状态推演。
