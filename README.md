# NIKKE 装备优化规划器

把「我现在该把石头花在哪」变成一个可排序、可复现的答案。

输入账号当前的装备状况与资源库存，输出一份**全局竞价天梯**：所有可行的养成动作
（升级 / 开光 / 洗词条 / 洗数值）放进同一个 ROI 公式里排队，告诉你下一步做什么
最划算。

---

## 它解决什么问题

NIKKE 后期资源的分配是一道典型的**组合优化**题，但凭直觉做会掉进三个坑：

1. **单看某个词条的最优解没用。** 「优越代码伤害 +11%」值不值得，取决于这个角色
   当前优越代码有几条、乘区稀释到什么程度。脱离角色现状谈词条收益是没有意义的。
2. **操作之间在抢同一份资源。** 升一级只要 15 万信用点，洗一次词条要 3 个石头，
   两者该怎么比？需要一个统一的换算（本项目用影子汇率：1 石头 = 150 万信用点）。
3. **角色之间也在抢。** 皇冠一条装弹词条能让她自身伤害涨 17.7%，爱丽丝只有 11.4%
   —— 但皇冠自身伤害可能只占全队 1%。按自身增幅排序，仓管角色会排到主力前面去。

本项目把这三层都做进同一个排序里。

---

## 三个核心设计

### 1. 五大乘区伤害模型

角色的相对伤害增益拆成五个独立乘区累乘：

```
伤害 ∝ (ATK) × (ELE) × (Ammo 占空比) × (CS 秒蓄门槛) × (Crit)
```

每个词条作用于哪个乘区、该乘区当前被稀释到什么程度，都从**账号实际装备**现算，
不用任何人工主观系数。Crit 乘区带边际衰减因子（实战中暴击收益极低）。

### 2. 方案级竞价，不是单次操作

目标是「达成某个词条组合」，不是「洗一次」。所以每条候选动作的成本是
**达成目标的期望成本**（无放回超几何选择 + 几何分布期望 + 2+3 累加锁词门票 +
渐进式洗数值期望 6.67 / 18.93 / 34.79 石），而不是单次尝试的花费。

### 3. 角色培养榜是主视图，档位是**次序**不是**倍率**

主输出一行 = 一个角色的下一步。为什么不把上千条明细平铺：用户的问题是
「我现在该把资源用到哪」，答案是**某个角色的某件事**；平铺还会让档位靠前的角色
被自己的几十条候选刷屏，把别的角色挤出视野。

排序规则是**档位优先，档内按 ROI**，而不是 `ROI × 档位权重` 一把梭 ——
后者会让 T2/T3 的便宜动作插到 T0 前面（实测 T3 的尼恩能排到第 9）。
T0 是永久保质期角色，投进去的每分资源都有回报，所以档位必须作为次序先起作用，
权重只用于同一档位内部比较。明细天梯仍然保留（CLI 加 `--detail`，GUI 里在下方）。

## 快速开始

需要 **Python ≥ 3.10**。

```bash
pip install -r requirements.txt
```

### 准备账号数据

程序需要一份**账号实际装备表**（上游格式：`{"角色": [{姓名, 战力, 头, 甲, 手, 脚}]}`，
每个部位含强化等级与 3 条词条的数值）。字段语义见 [`input/数据说明.md`](input/数据说明.md)。

本仓库**不含**任何真实账号数据。`input/cn_collect.sample.json` 是一份脱敏样例
（10 个角色），格式与真实文件完全一致，可以直接拿来试跑：

```bash
python3 main.py --input input/cn_collect.sample.json --stones 100 --credits 5000000
```

要跑自己的账号，把你的采集结果放到 `input/cn_collect.json`（该路径已在 `.gitignore`
中，不会被误提交）。

> **采集工具：** 推荐用 [Nikke-OCR](https://github.com/lcn225/Nikke-OCR) 从游戏截图
> 直接产出上述格式的 JSON。任何能产出该结构的方式都可以 —— 手工填表、游戏端导出
> 也行，本项目只认格式。

### 跑 GUI

```bash
python -m streamlit run app.py
```

Windows 下也可以双击 `启动GUI.bat`（该文件是 GBK 编码，配合 `chcp 936` 使用）。

GUI 功能：上传名册 → 设置资源库存 → 运行计算 → 角色培养榜（点行展开该角色的
全部候选动作）→ 明细竞价天梯 → 导出 CSV / 纯文本执行清单。每次计算会自动在
`data/history/` 存一份历史记录，可随时读回或删除。

### 跑 CLI

```bash
python3 main.py                                      # 交互式输入资源
python3 main.py --stones 100 --credits 5000000       # 指定资源
python3 main.py --detail --top 20                    # 附明细天梯（前 20 条）
python3 main.py --mode PVP                           # 换模式，默认 PVE
```

## 数据来源：三者分工，别混

这是本项目最容易搞混的地方。三类数据的**变化频率**和**归属**完全不同：

| 数据 | 文件 | 回答什么 | 多久变一次 | 入库 |
|---|---|---|---|---|
| **账号现状** | `input/cn_collect.json` | 我装备了什么 | 每次玩都变 | ❌ 个人数据 |
| **角色策略** | `data/targets_parsed.json` | 这个角色该怎么养 | 版本更新才变 | ✅ |
| **角色物理** | `data/character_physical_config.json` | 这把枪的基础数值 | 出新角色才变 | ✅ |

后两者是**全服通用的攻略/图鉴知识**，与账号无关，所以随仓库分发；
引擎运行时**只读本地文件、不访问网络**。

### 这两份数据文件是静态快照

`data/targets_parsed.json` 与 `data/character_physical_config.json` 随仓库一次性分发，
是**定稿的快照**。本工具运行时完全不联网 —— `requirements.txt` 里连 `requests` 都没有。

- 这两份文件**不要手工编辑**。`data/physical_overrides.json` 记录的是人工判定过的
  字段（如某些角色的机制例外），供查阅用，不参与运行。
- 快照若有更新，直接整体替换 `data/` 下的对应文件即可。
- 快照里缺的角色/字段（见下节「已知限制」）在本仓库内补不了。这不是保守，
  而是**不留兜底**：不知道的留空并报警，好过猜一个值出来。

## 一条贯穿全局的原则：不留兜底

抓不到的数据**留空 + 报警**，不猜、不补、不取最近档。理由很直接 ——
把「不知道」伪装成「知道」，比缺数据危险得多：

- 词条名不在标准名表里 → 直接抛 `KeyError`，不猜别名。
- 数值不在 15 档上 → 直接抛错，不取最近档（否则 OCR 错误会被当成合法数据）。
- 目标词条没接入 → 报告里明写「本结果只剩升级类竞价，**不代表已毕业**」。
- 角色物理参数缺失 → 跳过该角色并在榜上标注原因，不按默认值算。

上游补齐后重新生成数据快照即可自愈 —— 这条路径已经实证跑通过（见
`docs/ROADMAP.md` 与 `input/数据说明.md` 的相关记录）。本仓库只提供快照本身，
生成工具在外部。

## 已知限制

- **物理参数覆盖不全。** 少数角色（如雪子、QUEEN（真））在上游数据里射速那一格是
  空的，引擎会跳过它们并在榜上标出来。数据文件是静态快照，补不了 —— 这不是疏漏，
  见上文「不留兜底」。
- **档位权重是主观参数。** `config.py` 里的跨角色折算系数是全项目**唯一**一处
  人工主观系数，它只有**一个旋钮**、集中在一处、并且在报告里可见 —— 这是刻意的例外。
- **历史记录不含名册快照。** 读回历史时无法重建角色培养榜（会给出说明而不是假数据）。
  详见 [`docs/ROADMAP.md`](docs/ROADMAP.md)。
- **GUI 勾选「已完成」尚未实现。** 见 `docs/ROADMAP.md` 的 R2。
