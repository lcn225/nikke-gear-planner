# 妮姬国服「实际表」数据说明

这份文档说明「实际表」（默认文件名 `cn_collect.json`）的格式。它记录的是**你自己账号**的
装备状态，由游戏客户端截图 + OCR 读出，再经人工逐项校正，用来和「推荐表」对照、
算资源投入优先级（先升谁、先刷哪个词条）。

> 本文的**示例与统计全部取自随仓库分发的脱敏样例** `input/cn_collect.sample.json`
> —— 10 个角色 / 40 个装备槽，合成数据，不是任何真实账号。你自己采集的文件结构完全相同，
> 只是角色更多。样例的数字可以自行复核：
>
> ```bash
> python -c "from engine.roster_loader import load_roster as L; r=L('input/cn_collect.sample.json'); print(f'角色 {len(r.characters)} / 槽 {r.t10_slots+r.t9_slots} = T10 {r.t10_slots} + T9 {r.t9_slots} / 词条 {r.buff_lines} / 占位 {r.empty_placeholders}')"
> ```
>
> 两条恒等式对**任何**合法名册都成立，也可以拿来查自己的文件：
> `T10 + T9 = 4 × 角色数`；`真实词条 + 空占位 = 3 × T10`。

---

## 一、文件与结构

顶层是一个对象，唯一键 `角色`，值是一个数组，每个元素是一个角色。
下面这个例子摘自样例文件（原样摘录，不是编的）：

```json
{
  "角色": [
    {
      "姓名": "尼恩",
      "战力": 178536,
      "头": {
        "等级": 2,
        "词条": [
          {"名称": "防御力增加",     "数值": 0.0547},
          {"名称": "未获得效果",     "数值": 0},
          {"名称": "最大装弹数增加", "数值": 0.8126}
        ]
      },
      "甲": {
        "等级": 3,
        "词条": [
          {"名称": "最大装弹数增加", "数值": 0.4839},
          {"名称": "攻击力增加",     "数值": 0.1252},
          {"名称": "未获得效果",     "数值": 0}
        ]
      },
      "手": {"等级": 4, "词条": [ ... 固定 3 条，结构同上 ... ]},
      "脚": {"等级": 5, "词条": [ ... ]}
    }
  ]
}
```

这一行恰好能说明三件事：**`头` 是 T10（有词条）且等级 2**；**`头` 的第 2 条是空词条位**
（`未获得效果` / `0`，见第五节 `XEX` 形态）；**数值 0.0547 就是 5.47%**。

- `角色` 数组**顺序不承载语义**（大致按战力降序，但不要依赖它排序）。
- 文件名 `cn_collect.json` 只是采集脚本的默认名，提交时可自行改名，内容不受影响。
- 4 个装备槽固定为 **头 / 甲 / 手 / 脚**，对应游戏角色信息页 2×2 的左上/右上/左下/右下。
- 每个槽的 `词条` **恒为 3 条**，不足 3 条的用占位符补齐（见下）。

## 二、字段语义

| 字段 | 类型 | 含义 |
|---|---|---|
| `姓名` | string | 游戏内角色名，**主键**。 |
| `战力` | int | 角色战斗力，整数。样例里范围 120000 ~ 185853。 |
| `等级` | int / null | 该件装备的**强化等级**，取值 0~5。`null` = 该槽没有 T10 装备（见第三节）。 |
| `词条[].名称` | string / null | 词条名，见第四节的 9 个规范名。`"未获得效果"` = **该槽是 T10，但这个词条位是空的**。`null` = 该槽整个没有 T10（见第三节）。 |
| `词条[].数值` | float / null | 百分比**小数**：`0.1181` = **11.81%**。`"未获得效果"` 的数值恒为 `0`。 |

> ⚠️ **数值是小数不是百分数**。`0.1181` 请当 11.81% 用，别当 0.1181%。
> 全部数值最多 4 位小数，且**都精确落在合法档位上**（见第五节），可以直接当精确值用于计算。

## 三、T9 / T10 怎么区分

游戏里 T10 装备有「改造装备效果」那一整块（3 个词条位），T9 完全没有这块。所以：

| 该槽的 `词条` | `等级` | 含义 |
|---|---|---|
| 三条都是 `{"名称": null, "数值": null}` | `null` | **T9**（没有改造装备效果，属预期，不是漏读） |
| 至少一条有名称（含 `"未获得效果"`） | 0~5 | **T10** |

- 样例的 40 个槽里，**35 个 T10、5 个 T9**。
- **`"未获得效果"` 是 T10 的铁证**：它是游戏里空词条位的占位文字，只有 T10 才显示。
- `等级` 只在 T10 槽有意义；样例里 35 个 T10 槽**全部有等级，零缺失**。

## 四、10 种词条名（9 个规范名 + 1 个占位符）

`名称` 用的**就是游戏内的原文**，共 9 种，全部带「增加」二字：

| 名称 | 样例中出现次数 |
|---|---|
| `优越代码伤害增加` | 10 |
| `蓄力速度增加` | 8 |
| `攻击力增加` | 7 |
| `暴击伤害增加` | 9 |
| `蓄力伤害增加` | 9 |
| `最大装弹数增加` | 9 |
| `暴击率增加` | 8 |
| `防御力增加` | 8 |
| `命中率增加` | 9 |
| （占位符）`未获得效果` | 28 |

> ⚠️ **推荐表里的简称需要自行映射到上面这 9 个名字**，本表不做归一化、也不会输出简称。
> 已知的对应关系（供参考）：`蓄速`/`蓄力速度` → `蓄力速度增加`；`优越代码` → `优越代码伤害增加`；
> 带不带「增加」是同义的（本表一律带）。
> ⚠️ 注意 **`优越代码伤害增加` 是 6 个字**，不是「优越代码增加」。

## 五、词条位**不是**从上往下顺序填的（重要）

游戏里 3 个词条位可以**独立锁洗**，所以「中间空」是合法状态，不是漏读。本表实际出现的形态：

| 形态 | 含义 | 数量 |
|---|---|---|
| `···` | 三条全空 —— 该槽是 T9 | 5 |
| `XXE` | 前两条有词条，第三条空 | 10 |
| `XXX` | 三条全满 | 7 |
| `XEX` | **第 1、3 条有词条，第 2 条空** | **8** |
| `EXX` | 后两条有词条，第 1 条空 | 10 |

> 上表是**样例里实际出现**的形态。不同名册出现的形态集合不同 —— 规则不变，数量会变。

> 解读时**建议按「集合」处理这 3 条词条**（有几条、分别是什么），不要假设它们会紧凑地填在前 N 个位置 ——
> 否则 `XEX` 那 8 个槽会被误判成「只有 1 条词条」。
> 位置本身只表示游戏里的显示顺序，**不代表优先级或洗练顺序**。

## 六、数值的合法性

样例里全部 77 条真实词条的数值（共 43 个不同的值）**都精确落在合法档位上**，来自游戏内「词条数值表」
（9 词条 × 15 档）。核对结果为 **0 条越档**。

因此下游可以直接：
- 用数值精确匹配档位（示例：`攻击力增加` 的 15 档为
  `0.0477 / 0.0547 / 0.0618 / 0.0688 / 0.0759 / 0.0829 / 0.09 / 0.097 / 0.104 / 0.1111 / 0.1181 / 0.1252 / 0.1322 / 0.1393 / 0.1463`）；
- 或需要「第几档」时，用该词条的档位表反查下标（0 基）。

## 七、本表只有账号现状，**不含养成目标**

这里是全项目最容易踩的坑，单独列一节。

本表回答的是「**我装备了什么**」——谁、什么等级、哪些词条、什么数值。它**不回答**
「这个角色该怎么养」。后者的答案是全服通用的攻略知识，来自上游推荐表，
每季版本更新才变一次，与本表的「每打一次装备就变」完全不是一个变化频率。

两者混在一起的后果：养成目标会被降级成「每个账号各维护一份」的静态副本，
上游攻略一更新，你手上那份就悄悄过期了，而且没有任何信号告诉你它过期了。

所以数据源**一分为二**，物理上分离存放：

| | 回答什么 | 放哪 | 变化频率 |
|---|---|---|---|
| **账号现状** | 我装备了什么 | 本文件 `cn_collect.json` | 每次玩都变 |
| **角色策略** | 这个角色该怎么养 | `data/targets_parsed.json`（清洗后的快照） | 几乎不变 |
| **角色物理** | 那把枪的基础数值 | `data/character_physical_config.json` | 新角色实装时 |

> 本表**不承载**、也不应该承载任何目标词条字段。引擎侧由
> `engine/roster_loader.py` 读本文件拿到装备现状，目标词条另从
> `data/targets_parsed.json` 读出后注入 `Character.targets` —— 两条路在引擎里才汇合。
>
> 后两份是**随仓库一次性分发的定稿快照**。

> 历史上这三者曾被塞进同一张 Excel（`Nikke.xlsx`，含 `目标1主副 / 目标1词条 …` 列），
> 该文件与读它的 `excel_to_my_roster.py` 已于 2026-09-25 归档到 `legacy/`，不再参与流程。

## 八、数据质量现状

本表是 OCR 产物，绝大多数已人工核对。

**读不出来的字段一律留空 + 报警，不猜。** 不补默认值、不取最近档 —— 这与
「不把不知道伪装成知道」是同一条。曾经有一处 `数值` 是 `null`，引擎如实报出而不是拿
相邻档位顶上；上游补齐后重抓即自愈。这条路径已实证跑通。

- **脏数据的处理逻辑有专测守着**：`test/test_new_functions.py` 的
  `test_roster_dirty_data_handling` 用**合成输入**覆盖三种空态（整槽全空 = T9；
  `未获得效果` = T10 的空词条位；有名无数值 = 脏数据留空报警），不依赖真实数据恰好脏着
  —— 上游把数据修好之后，这套逻辑照样有人守。
- **本机名册的具体修正记录不入库**：哪几行出过什么问题、修正前后的战力是多少，
  属于账号内容，记在 `input/数据质量记录.md`（本机私有）。公开文档只讲格式与规则。

**1. 姓名可能与图鉴的写法不同**：图鉴里基础角色（如 `索林`）和「名字：称号」变体
（如 `索林：霜之旅票`）是**两条独立词条**。本表用的是游戏横幅上读到的名字，采集时需人工
核对到具体是哪一个变体；如果你手上的角色名单写法不同，请以 `战力`/装备作为交叉验证。

**2. 名字里的全角冒号**：「名字：称号」变体用的是全角 `：`。做字符串匹配时建议先统一全角/半角。

**3. 角色数 = 账号当前拥有的角色数**，不是全图鉴，会随着抽卡增长。四槽全是 T9 的角色，
其装备字段整块为空（`名称` / `数值` / `等级` 全 `null`），属预期，不是漏读。

## 九、如何复核 / 重新生成

配套的校正工具 `correct_gui.py` 就在同一个目录：

```bash
python correct_gui.py --report      # 不开窗，打印所有存疑项清单
python correct_gui.py --roundtrip   # 读入→原样写出→读回，验证格式零改动
python correct_gui.py               # 打开界面，逐项人工校正
```

- `--report` 会打印每一行的可疑分级：`▲` 必须翻回游戏核实、`!` 可靠已有信息修正。
- JSON 每次保存前会**自动留底**成 `cn_collect.<时间戳>.json`，所以目录里若有多个带时间戳的文件，
  **`cn_collect.json` 才是最新版**。

## 附：一句话速查

- 每行 = 姓名 + 战力 + 头/甲/手/脚，每槽 = 等级(0~5 或 null) + 3 条词条(名称 + 小数数值)。
- **数值 ÷100 就是百分比**；**T9 槽 = 词条全 null**；**`未获得效果` = T10 的空词条位**。
- **3 条词条不要按顺序读**，`XEX` 形态在样例里有 8 个槽。
- **所有计数都会随账号变**：本文的示例与统计取自入库的脱敏样例
  `input/cn_collect.sample.json`；你自己名册的现状跑 `python test/test_new_functions.py` 看。
